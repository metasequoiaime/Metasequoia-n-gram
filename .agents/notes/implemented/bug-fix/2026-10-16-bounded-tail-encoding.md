# Agent Note: 候选编码只覆盖模型评分窗口

Status: implemented

## Problem

#53 直接移动候选编码后，`Vec::truncate` 只缩短长度，原始容量会进入 `resume`。合成的 65536 字候选在 8 位置模型上只评分 7 个 token，却保留 98306 个 token 容量；原来复制截断切片的路径只持有 7 个 token。评分前完整编码还执行了不会参与前向的词表查询。

## Decision

候选编码前计算同一个评分窗口，只消费前 `limit` 个 Unicode scalar。完整编码调用继续不设上限。候选 token 顺序、未知字映射、上下文窗口预算、完全命中和部分续跑逻辑保持。编码结果直接移动，不重新缩容或复制。

## Alternatives considered

- 截断后 `shrink_to_fit`：恢复容量上界且改动小，但长候选仍完整编码并多一次重新分配，抵消所有权转移的用途。
- 按 UTF-8 字节直接截断：切片成本低，但 token 按 Unicode scalar 定义，任意字节边界既可能 panic，也会改变候选评分范围。

## Verification

容量预算测试在旧代码上真实失败：7 个评分 token 保留 98306 容量。修改后，65536 字的汉字、ASCII 和 emoji 在冷、热两轮均只编码 7 个 token，保留容量受窗口约束。固定 #53 评分流程进行 180 轮对照，覆盖上下文改变、长短切换、候选重复和顺序变化、未知 token 与空串，分数位模式、缓存 token 顺序、KV 与累计分均相同。既有三精度缓存序列和原位移动测试保持通过。Rust 1.97.1 与最低版本 1.75.0 均通过 23 个单元测试和 14 个模型文件测试，Clippy 全目标、fmt 与差异检查通过。

## Consequences

`collect` 有标准库最小容量和增长策略，测试限制的是窗口数量级，不能要求所有长度刚好等于 token 数。最长候选的字符计数仍扫描完整文本，不能声称整个入口对超长文本变为常量工作。

每候选编码和持有 token 的空间从原始文字长度收敛到模型窗口；不增加新缓存、依赖或公开 API。完整编码入口保留原行为，分数和前向次数不变。这修复 #53 移动所有权后暴露的容量回退，不承诺九键端到端达到 16 ms。
